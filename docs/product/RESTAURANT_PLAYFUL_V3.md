## 2. 設計方向：先會招待一個客人，再學經營
**孩子的主動作：看餐點圖 → 點食材做一份 → 點客人上菜 → 看錢包增加。**
能力聚焦策略與取捨；不宣稱已證實提升智力。

V2 已有圖像與場景，困難仍在「先規劃六份、理解兩批、先做好才開店」的流程。V3 不能只換皮；預設改成一位客人一個小循環，經營選擇在開店前與打烊後逐步出現。

資訊層次：
1. 當下：一位客人、餐點泡泡、料理台、當下可用食材、錢包及一句短提示。
2. 下一步：一個主要動作，例如「煮好了」或「送上桌」。有替代餐才顯示兩張圖。
3. 按需：小帳本、份數／包數、完整成本、六位客人總覽與食材期限。

主場景占遊戲區約 2/3；不做側欄儀表板。手機先保住客人、鍋、盤與操作列，裁掉遠景，不把整個桌機畫面縮到看不清。這種構圖直接服務做餐與交餐，而非讓孩子找一串流程按鈕。

## 3. 第一個可交付增量 R1：一間店、完整一天
先交這一輪，不等新菜、七日養成或全部美術。使用現有三道菜與原創角色素材，預設兩種飯；低支援負荷模式最多選兩道，仍能改選吐司，不能把「選要賣什麼」刪掉。

### 開店前：兩個選擇就進廚房
- 「今天賣什麼」：三張實物餐點圖卡，預選番茄蛋飯＋蔬菜蛋炒飯，可改為 1–2 道；選取用輪廓＋勾選＋名稱。沒有數字輸入欄。第三道欲選時說「先選兩道」，點已選的圖可換；不默默替孩子取消。
- 「一起買齊」：系統列一籃合併食材與總花費，孩子可返回改菜單或確認採買。錢包顯示買前／買後，固定費用 50 保留。所有數值由引擎算，不硬寫 117。
- 系統建議份數使用已公開的固定六位教學客人：每人先取已上架首選，否則取已上架且能負擔的替代餐，否則不配餐；總量加總後扣庫存、整包採買。明示「幫你算好份量」；這是新手支援，不把替孩子計算說成孩子已經會規劃。
- 進階「自己規劃」可在開店前選擇，保留 V2 的 1–3 道、手動份數與包數及分批備餐。模式在一次營業開始後不切換；僅展開帳本不更換模式。
- 無需先輸入年齡、登入、完成長說明或答題。首次第一份上菜設計目標 60 秒內，需真實孩子驗證，尚非已達成結果。

### 營業中：看得到客人才做菜
- 客人先站在櫃台，泡泡顯示首選與可接受替代餐，順序與預算沿用現有資料；不顯示猜謎長對話。
- 點要做的餐點，料理台顯示三個食材輪廓。第一、二份讓孩子點米／蛋／番茄或青菜入鍋；順序不限，點錯可拿回，不能產生隱形扣料。包裝由系統配入，計入成本，不多設一個教學步驟。
- 食材選擇只是可還原的草稿；點「煮一份」才檢查全套原料、容量並一次扣料產生成品。食材不足時整次拒絕、指出缺哪一個，不能部分耗用。
- 第二份完成後提供「直接做一份」捷徑，省下重複點同樣食材；仍可選「自己放食材」。捷徑不自動替孩子選餐、上菜或花錢。兩者使用相同食譜與成本。
- 成品放在明顯的餐盤區，再點餐盤／「送上桌」；有多份時先選盤。可選拖曳，但點選與鍵盤必須等效。收款只在送給接受該餐的客人時發生，金幣不是額外再點才領取。
- 仍使用同一共用庫存。第一份用蛋 6→5，第二種菜再用同一箱蛋 5→4；不為每道菜複製蛋箱。點蛋箱可看到所有上架且用蛋的菜，圖示＋連線／括號＋名稱，不只變色。
- 新手流程的第 1–3 位／4–6 位保留內部兩批，每批最多 4、全日最多 8；批次切換由已處理完的訂單事件推進，孩子不用額外按「開始上菜／結束這批／再做下一批」。不能跳過未處理客人，也不能依動畫結束推進規則。
- 做錯客人不收的餐，餐盤保留，提示「這份先留著」；改做合適餐、之後再給可接受者。食材已煮不能拆回；沒送出的熟食打烊才報廢。
- 沒有可送出的成品但仍能煮合適餐，主動作是「做一份」；完全無法滿足時才提供「今天沒有」。維持「有可售成品時不能記成未成交」原則。無原料／零採買也能走到打烊。
- 沒有倒數、手速分數、憤怒倒數條；暫停與離開不處罰。

### 打烊：一個取捨
主畫面顯示「服務 {n} 位」與錢包；結餘與完整分類在「看看今天」／帳本。只給一條依真實結果產生、可略過的提示，例如「兩道菜，都用了蛋」或「有一份沒賣掉」。
- 盆栽 120 與「先存起來」並排。點盆栽先在固定位置預覽；按「買 120」才扣款，預覽可取消。
- 購買後盆栽真的出現在店裡，已有的不能重複扣款。純裝飾、不增加客流或今日結餘。
- R1 不增加第二天或全店裝潢商城。「再玩一次」保留確認與上一局紀錄，不因打烊自動重置錢包。連續經營留 R2，不能把重玩當成存貨延續。

共用清單必須先加總才向上買整包；兩道飯合計 117 對照分開錯買 201，少占用 84 現金，並非單份變便宜或立即多賺 84。庫存可用部分仍是資產；備餐扣原料，採買扣現金，打烊不能重複扣食材款。
- 本日結餘＝收入－賣出成本－熟食／到期原料報廢－固定費用。
- 現金＝開店現金－實際採買＋收入－固定費用－裝飾。
- 所有金額是遊戲幣，沿用遊戲平衡數值。

## 6. 工程契約：這輪必須改什麼
- 重用 `shared/restaurant/data.ts` 與 `engine.ts`，不可把設計 demo 複製成第二套正式經濟引擎。
- 目前 `prepare` 只允許 prep，不能直接在 UI 假裝已能一邊接客一邊做菜。新增明確的 guided 服務流程／動作驗證，與 classic 分批流程分開記錄；共用採買、原料耗用、成交、費用、結算函式。保留原 classic RT01–RT14。
- 料理草稿（餐點、已選食材）、模式、目前客人、未送出採買草稿、已提交動作 id 與裝飾預覽分開。預覽不入帳；同一訂單不能重複成交。批次內未處理訂單不可被自動跳過。
- 新增版本化存檔，推薦獨立 `jy.restaurant.v3`。舊 `jy.restaurant.v1` 原文保留，不自動覆寫；舊局繼續走 classic，新增「玩新版」可另存開局。舊完成局的 414／盆栽不能因開 V3 消失。新舊兩局的錢不能混用。
- 載入 schema 驗證、寫後讀回驗證；損壞／較新版本先備份並確認，再允許遷移。備份失敗保留原鍵，另存也失敗時留畫面並明示未存好。提供下載進度；不得先顯示已存好再等重整才發現讀不回來。
- 本輪原碼風險：V2 constructor 的備份失敗會落入 catch 並用 newGame；後續 save 直接寫主鍵且沒有讀回。這是 source review 疑點，**本輪沒有對正式站注入壞檔重現**。R1 必須以隔離儲存案例驗證並處理，不照抄這段；可借用塗鴉已驗收的備份／另存／讀回原則，不能直接把兩遊戲的 schema 合併。
- 暫停、切背景、旋轉、重整、重送、快速雙擊、兩分頁舊版本不得多扣料／多收款／回蓋新局。動畫時鐘不是交易來源，減少動態不能改變經濟結果。
- Canvas 2D＋SVG／DOM 足以做 R1；Three.js 依原授權可用，必須逐路由載入及保留可讀屏 DOM 控制，不把換渲染器當開工門檻。

## 7. 驗收與交付順序
先交 **R1-a：兩道預設飯＋採買＋第一、二位客人完整圖像操作＋續玩** 的可玩預覽，再補成 **R1-b：六位客人、改選吐司、缺料／替代餐、盆栽與進階入口**。R1-a 尚非完整一天驗收通過；不等 R2 才交第一個版本。沿用 /restaurant、/en/restaurant 的 noindex 試玩入口，更新需保留舊局續玩。

| ID | 必須有可重現結果 |
|---|---|
| R3-01 | 無帳號開始；1–2 菜可更換；預設計畫與採買由客人／菜單／庫存推導，取消菜會重算；不打開帳本可送出第一份 |
| R3-02 | 新手客人先出現，三食材點選／移除／確認、成品送餐；錯配不扣款，缺料整次拒絕，替代餐與今天沒有可用 |
| R3-03 | 第一、二種飯共用同一蛋箱 6→5→4；選菜能追溯需要的食材；117／201／84 對照準確，不假稱折扣 |
